# 产线缺陷分数推理 · 双路成对出分 · 单帧缺口补算

FastAPI 推理网页：内置固定权重的 NumPy 递推模型和两路样例。同一工件的两个相机视角
**成对提交、一起出分**；按相机 + 帧号提交 8 维特征向量，每路允许暂缺一帧；补交原帧后
从缺口前的状态按帧序补算，补算追上本路最新已出分帧后才把修正状态交给后续推理，已发
分数不改。

## 启动

```bash
docker compose up --build
```

打开 <http://localhost:8000> 。网页里可以：

- 「试跑：双路成对提交」——一笔同时送两路下一帧，共 8 笔，含缺口暂估与补算后恢复实测；
- 「演练：成对提交并发冲突」——成对计算期间从单路插入一帧，整笔 409 退回、刷新后重试；
- 「成对提交」面板——一次填写两路各自的下一帧号和 8 维特征，可直接用两路样例下一帧填充；
- 「试跑：边补帧边进新帧」——缺口补算与新帧交错的完整演示（A 路缺第 4 帧、B 路缺第 8 帧）；
- 每个相机卡片里单步「送入下一帧 / 标记缺失 / 补交原帧 / 补算故障演练」；
- 「手动提交一帧」表单按相机和帧号提交任意 8 维特征向量（单路，成对计算期间照常可用）；
- 「成对提交记录」与「操作记录」里核对每笔 `pair_id`、出分、暂估、补算范围和修正量。

不用 Docker 也可以本地跑（Python ≥ 3.11）：

```bash
python -m pip install -r requirements.txt
python -m uvicorn app.api:app --host 0.0.0.0 --port 8000
```

## 成对出分规则怎么落实的

| 需求 | 实现 |
| --- | --- |
| 同一工件两个视角成对出分 | `POST /api/pairs` 一次携带两路 `{camera, frame_no, features}`，每路按自己的状态递推，两路帧、分数、状态在同一临界区原子提交，共用一个 `pair_id` |
| 质检员一次填写两路下一帧号和 8 维特征 | 网页「成对提交」面板每路一个帧号 + 特征输入，「用两路样例下一帧填充」一键带入 |
| 各路按自己的状态递推 | 准备阶段分别快照每路 `state`，锁外各自 `model.step`，互不共用隐状态 |
| 两路的帧、分数和状态一起生效 | 提交阶段按相机号升序固定顺序持双锁，通过版本检查后才同时 `_emit`；要么两路都写，要么都不写 |
| 查双路汇总不能只看到一笔的一路 | `GET /api/status` 按固定顺序持双锁取一致快照；`GET /api/pairs` 每笔记录都含两路条目；分数行带 `pair_id` 可双向追溯 |
| 任一路校验或计算失败，两路都不生效 | 载荷校验在任何快照/写入之前；准备阶段任一路不合法直接抛错；锁外计算异常整体中止，均无任何写入 |
| 成对计算期间单路送帧和补算照常推进 | 模型计算不持任何相机锁；单路 `POST /frames`、`/missing`、`/fill` 不被成对请求阻塞 |
| 发布前任一路出新分/完成补算/被重置则整次退回 | 每路维护单调 `version`（送帧、开缺口、补算提交、重置都递增）。准备时快照版本，提交时重检，不一致返回 `409 pair_conflict`、`refresh_required=true`，前端提示刷新后重试 |
| 有缺口的相机先出暂估分 | 缺口未补时该路成对帧 `estimated=true`，另一路仍为实测；新帧随本路缺口在补算时一并重放 |
| 已发分数照旧保留 | 补算只写 `revised_score/delta/revision`，`score` 与 `pair_id` 均不覆盖 |
| 固定权重 NumPy 递推模型 | `app/model.py` 里的权重字面量，`GET /api/model` 给出权重指纹，运行时不训练 |

### 三阶段提交流程（乐观并发控制）

1. **准备（锁内、无写入）**：按相机号升序取双锁，校验两路帧号都是本路下一帧、未出过
   分，快照各自 `state` 与 `version`；
2. **计算（无锁）**：两路分别做模型递推。此期间单路送帧、补算、重置都可正常发生；
3. **提交（注册表锁 + 双锁）**：重检两路 `version` 与最新帧位。任一变化 → 抛
   `pair_conflict`，两路均不写入；否则分配单调 `pair_id`，两路同时落分并记入成对历史。

> 成对提交只接受每路**下一帧**（不允许在成对请求里跳帧）；缺帧仍走单路「标记缺失」，
> 这样缺口的打开与补齐始终是显式动作。

## 缺口补算规则（原有能力，保持不变）

| 需求 | 实现 |
| --- | --- |
| 每路允许暂缺一帧 | 每相机维护 `last_frame`；下一帧跳过一个帧号即打开缺口，缺口未补时不允许再缺第二帧（`409`） |
| 用零向量代入、受影响分数标暂估 | 缺口帧以零向量推进，`estimated=true`；缺口未补期间后续帧从临时状态继续出分，同样标暂估 |
| 补交原帧后从缺口前状态按帧序补算 | 开缺口时保存 `state_before`，补交时从它开始逐帧重放缺口帧到最新已出分帧 |
| 两路仍照常接帧、出分 | 每相机独立锁，补算在锁外做模型运算；其它相机和本相机新帧都不被阻塞 |
| 追上本路最新已出分帧才切换状态 | 重放目标取当前 `last_output_frame`，每帧检查是否又长了；追平后才一次性提交修正状态 |
| 已发分数不改 | `score` 字段只写一次；修正值写入 `revised_score/delta/revision`，界面两列并列 |
| 补算失败按原状态出分、可重试 | 重放期间不提交任何状态；失败返回 `422 {"retryable": true, "state_preserved": true}`，缺口和临时状态原样保留 |

模型：`h_t = tanh(W x_t + U h_{t-1} + b)`，`s_t = sigmoid(v·h_t + bias)`，
8 维输入、6 维隐状态、分数 0–1。样例数据在 `app/data/samples.json`，两路各 18 帧，
A 路第 6/7 帧、B 路第 5/10 帧带明显缺陷特征，方便观察分数跳变。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/health`、`/api/model`、`/api/samples` | 健康检查、模型信息、样例数据 |
| GET | `/api/status` | 两路一致快照汇总（缺口、暂估数、补算数、成对帧数、版本号、最近一笔成对提交） |
| GET | `/api/pairs?limit=N` | 成对提交历史（最新在前，每笔含两路条目） |
| POST | `/api/pairs` | 成对提交：`{items:[{camera, frame_no, features[8]} ×2], compute_delay_ms?}` |
| GET | `/api/cameras/{camera}/state` | 状态、分数（含 `pair_id`/修正值）、事件、版本号 |
| POST | `/api/cameras/{camera}/frames` | `{frame_no, features[8]}` 单路提交一帧 |
| POST | `/api/cameras/{camera}/missing` | `{frame_no}` 声明该帧缺失 |
| POST | `/api/cameras/{camera}/fill` | `{frame_no, features[8], pace_ms?, simulate_failure?}` 补交并补算 |
| POST | `/api/reset` | `{confirm: true}` 清空（补算中的任务会被取消且不提交；成对历史清空、版本号继续递增） |

成对提交的错误契约：

- `422 invalid_pair` / `invalid_frame`：载荷本身不合法（路数不对、相机重复/未知、特征
  不是 8 个有限数、帧号越界等），任何状态都不变；
- `409 conflict`：帧号不是本路下一帧或已出过分，返回 `expected_frame` 供前端纠正；
- `409 pair_conflict`：乐观锁失败，`refresh_required=true`，`conflicts[]` 逐路给出原因
  （版本变化或帧位移动），两路均未写入，刷新后用新的下一帧重试即可；
- `compute_delay_ms` 与 `pace_ms`、`simulate_failure` 一样是演示开关，生产部署前应移除
  或加权限。

## 验证

```bash
python -m pip install -r requirements-dev.txt
python -m pytest                       # 39 个单元/接口测试
python scripts/check_interleaved.py    # 缺口补算端到端：边补帧边进新帧
python scripts/check_pairs.py          # 成对出分端到端：原子性 + 并发冲突 + 刷新重试
```

`scripts/check_pairs.py` 自己拉起一个本地 uvicorn，逐条打印 PASS/FAIL：

1. 成对提交两路原子生效、`pair_id` 同时挂在两路分数上，各按本路状态递推；
2. 缺口相机在成对提交里出暂估分，另一路仍实测；
3. 成对计算期间单路送帧不被阻塞，但该笔成对提交被整次 `409` 退回、两路都不写入；
4. 刷新后按两路各自下一帧重试成功；
5. 成对计算期间 reset 同样整笔退回、成对历史清空、版本号不归零；
6. 缺口补算修正成对暂估帧，已发分数与 `pair_id` 保留，修正值与无缺口重算逐位一致；
7. 双路汇总与成对历史始终每笔两路齐全，不会只看到一笔提交的一路。

## 边界与未完成

- 状态只存在进程内存里，重启即丢；没有持久化、没有多副本共享状态。多副本下乐观锁
  `version` 需要换成共享存储里的版本号。
- 相机只支持两路（0/1），是配置常量而不是数据库配置；成对接口强制恰好每路一条。
- 成对提交只接受每路下一帧，不支持在成对请求里跳帧；缺口必须通过单路缺失接口显式打开。
- 每路同一时间只允许一个缺口；缺口窗口内再出现第二个零向量帧时，补算会明确拒绝
  （`422`）而不是猜，需先人工处理数据。
- `compute_delay_ms`、`simulate_failure` 是演示开关，生产部署前应移除或加权限。
- 没有鉴权、限流和审计日志落盘；事件只在内存里保留最近 500 条，成对历史保留最近 200 笔。
- 没有做真实产线帧率/吞吐压测，只有并发行为测试（含多线程竞态与端到端 HTTP 演练）。
